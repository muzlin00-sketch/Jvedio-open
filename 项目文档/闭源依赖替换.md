# 闭源依赖替换：SuperUtils

> 建立于 2026-10-29。本文记录**决策、约束与进度**，实施细节见各类型源码注释。
> 相关：[MAINTAINING.md 的「闭源依赖」节](../MAINTAINING.md#闭源依赖重要)。

## 一、术语纠正：这里的「闭源」指什么

`SuperUtils.dll` 并不是第三方商业库，它是本项目上游作者 **user（SuperStudio）** 自己写的
通用工具库，和 `SuperControls.Style.dll` 出自同一作者——Jvedio 本身也是他的项目。

说它「闭源」是指**本仓库里只有编译好的二进制，没有它的源码**：文件躺在
`Jvedio-WPF/Jvedio/Reference/` 下，谁也没有 `.cs`。后果是：

- 出 bug 只能在外面猜和绕，改不进去；
- 无法适配高 DPI、新 .NET、跨平台（这也是 `Jvedio.Core` 迁移 netstandard2.0 时
  被它卡住的原因）；
- 关键算法（识别码、文件哈希、ORM 建表）只能靠反推复刻。

它提供的能力（就是我们一直在用的那些）：

| 命名空间 | 干什么 | 在本项目里的份量 |
|---|---|---|
| `SuperUtils.Framework.ORM` | 自研轻量 ORM：`Where` 条件构造、`[Table]`/`[Column]` 特性、建表与增删改查、`Sqlite` 封装 | 最重，`Where` 一个类型 116 处引用 |
| `SuperUtils.Framework.Tasks` | 任务基类 `AbstractTask`（进度/状态/事件/取消） | 3 个任务派生类 + 41 处 `TaskStatus` |
| `SuperUtils.Framework.Logger` | 日志基类，本项目 `Logger` 直接派生自它 | 全部日志输出 |
| `SuperUtils.NetWork.*` | `HttpClient`/`HttpHelper`/代理/`HttpResult` | 刮削、下载、更新检查 |
| `SuperUtils.IO` / `Common` / `Security` / `Media` / `Systems` / `Reflections` | 文件、目录、剪贴板、JSON、哈希、图片、Win32、反射 | 到处都在用 |
| `SuperUtils.WPF.*` | `ViewModelBase`、`RelayCommand`、`ObservableString`、`VisualHelper`、`DataLoader` | 界面层基础 |

## 二、为什么不能「把 DLL 删掉」

曾尝试的路线是：把这 40 个类型逐个用本地实现替换，最后删掉 `SuperUtils.dll` 引用，
让文件从输出目录消失。**这条路走不通**，因为另外两个闭源库自己就依赖它：

```
SuperControls.Style.dll  ──TypeRef──▶ SuperUtils   （29 个类型）
CommonNet.dll             ──TypeRef──▶ SuperUtils   （ 2 个类型）
```

只要 `SuperControls.Style` 还在（2.3MB WPF 控件库、200 处引用、49 个文件，不在本次范围），
`SuperUtils.dll` 就必须存在于输出目录，否则控件库加载失败。

## 三、采纳的方案：用我们自己的源码编一个同名 `SuperUtils.dll`

即**把闭源二进制替换成仓库内的源码构建产物**，程序集名仍叫 `SuperUtils`。

**可行性已验证**：

| 检查项 | 结果 | 含义 |
|---|---|---|
| 是否强名称 | 否，无 `PublicKeyToken` | 非强名称程序集**按简单名绑定，忽略版本号** |
| 程序集版本 | 1.2.0.0 | 自编版本号不同也能绑定 |
| 闭源库的 AssemblyRef | `SuperUtils, Version=1.2.0.0, 无公钥标记` | 同上 |

因此自编的 `SuperUtils.dll` 会被 `SuperControls.Style` 和 `CommonNet` 正常绑定。

### 需要的 API 面比想象的小

用 `System.Reflection.Metadata` 精确枚举闭源库对 SuperUtils 的 **MemberRef**（不只是 TypeRef），
得到真实调用面：**26 个类型、58 个成员**。`CommonNet.dll` 虽然引用了 `HttpResult`/`RequestHeader`
两个类型，但**一个成员都不调**，只把它们当不透明类型传递。

（完整清单与校验方法见第五节。）

### 与「本地实现」的关系

两者不冲突，是同一件事的两个阶段：

1. 我们把每个类型按原 API 用源码实现——这部分工作照旧，且必须做（我们的代码也在用）；
2. 这些实现最终**编译进 `SuperUtils.dll`**，而不是散落在 `Jvedio.Common.*` 里各写一份。

所以已经替换掉的类型（`FileHelper`/`DirHelper`/`ClipBoard`/`Encrypt`/`ObservableString`/`AbstractLogger`
等）要逐步**迁回 `SuperUtils.*` 命名空间**，避免同一份逻辑存在两处实现。

## 六、网络层的复刻要点（易踩）

网络层是"能用"和"和原来一样"差距最大的一簇，以下几点都是照原实现抠出来的：

1. **没有 Success 判断**。HttpResult.Success 在原实现里从未被赋过值，恒为 alse；
   真正判断出错的方式是 `Error != HttpResult.DEFAULT_ERROR_MSG`（默认哨兵是字符串
   `"HTTP NOT OK"`）。请求成功时 Error 仍保留哨兵值，不会清空——看到 `Error="HTTP NOT OK"`
   加非空 SourceCode 是**正常成功**。
2. **两层超时**。外层是 `NetSetting.HttpTimeout`（单位**秒**，包住整次请求，超时抛
   TimeoutException），内层是 `RequestHeader.TimeOut`（单位**毫秒**，给 BCL 的
   `HttpClient.Timeout`）。调用处普遍写 `HttpTimeout * 1000` 就是在这两者之间换算。
3. **超时文案是写死的** `HTTP TIME OUT`（全大写、带空格），不是异常消息——
   UI 与任务日志都靠这个字符串识别超时。
4. **Host 头无条件补一条**；请求头里的 `cookie`/`cookies` 不当作普通头，
   而是按 `a=1; b=2` 解析进 CookieContainer；`user-agent` 必须走
   `UserAgent.ParseAdd`，用 `Add` 会因格式校验抛异常（代码里用 try/catch 兜住其它头）。
5. **SOCKS 代理不走 WebProxy**。.NET 的 WebProxy 不支持 SOCKS，
   原实现用 `MihaZupan.HttpToSocks5Proxy`；且无账号密码时必须用两参数重载，
   否则该库对 null username 抛 ArgumentNullException。
6. **HttpMode 的整数值有意义**（String=0 / Header=1 / Stream=2），历史调用方按整数传参。
7. AsyncGetWebTitle 取不到正文时抛 WebException；AsyncDownLoadFile 只有
   `StatusCode == 200` 才返回，否则抛 WebException——异常交给外层换源/重试，不要在内部吞。

**边界妥协**：SuperUpgrader.Header 的声明类型来自 SuperUtils，目前只能先构造旧类型
（Upgrade\UpgradeHelper.cs 里有 TODO 标注）。这类"控件库签名绑定 SuperUtils 类型"的点，
要等自建 SuperUtils.dll 落地后统一收口——那时让兼容层的类型**派生**自 Jvedio.Core.Net
的同名类型即可，不必改动调用方。
## 七、任务簇的复刻要点（易踩）

`AbstractTask` / `TaskDispatcher<T>` 的语义是从 IL 反推的，几处反直觉行为**必须保持**：

1. **`Status` 赋值会覆盖 `StatusText`**：命中 `STATUS_TO_TEXT_DICT` 就用字典文案，否则置空。
   所以「先 `StatusText = ex.Message`、再 `FinalizeWithCancel()`」会把错误信息冲成 `Cancel`——
   现有调用方（截图/下载/扫描任务）都落在这个顺序上。
2. **`STATUS_TO_TEXT_DICT` 是静态共享字典**，各子类在自己的静态构造函数里覆盖同名键，
   后加载者生效；`Running` 的文案因此可能是"扫描中……"或"下载中……"，取决于加载顺序。
3. **`TaskStatus` 用的是 BCL 的 `System.Threading.Tasks.TaskStatus`**，不是自定义枚举。
   于是 `TaskStatus.Canceled | TaskStatus.RanToCompletion`（值为 7）永远不等于任何真实状态，
   `BaseManager.RemoveTask` 专门为此写了特判分支。
4. **`Start()` 捕获 `DoWork` 的异常**：记 `e.ToString()` 与 `StackTrace` 两条日志后走
   `FinalizeWithCancel()`，异常不会抛给调用方。
5. **调度循环每轮固定休息 200ms** 并补发一次 `onLongDelay(this, "0")`，
   长延迟分支结束后也一样；`Progress` 用浮点除法，总数为 0 时得到 NaN 而非抛异常。
6. **`NumberHelper.GenerateRandomMS(value, max)` 实际取值恒在 `[0, max)`**，
   第一个参数只是位移、不影响范围（等价于 `new Random().Next(-value, max - value) + value`）。
   契约上"以它为准"的注释会误导，已在本实现里写明。

## 八、WPF 簇的复刻要点（易踩）

1. **`ViewModelBase.Init()` 是抽象方法**。基类只提供 `RaisePropertyChanged` 和事件，
   派生类必须实现 `public override void Init()`（现有 9 个视图模型都已实现）。
2. **`RaisePropertyChanged` 必须带 `[CallerMemberName]`**。调用点大量写无参形式，
   去掉这个特性会让所有属性名变成 null，界面静默不刷新——最难查的一类故障。
3. **`RelayCommand<T>` 的判据是 `Func<bool>`（无参）**，不是 `Func<T, bool>`。
   名字看起来该拿到命令参数，实际拿不到；照直觉改成带参会编译不过既有调用点。
4. **`VisualHelper` 的查找方法是扩展方法**（`this FrameworkElement`）。
   注意：通过 `using static` 导入后，扩展方法**不能**再用静态形式 `FindXxx(obj, ...)` 调用，
   必须写成 `obj.FindXxx(...)`。仓库里两种写法都有，改的时候看调用点形态。
5. **`SerializeBrush`/`RGBAToBrush` 的颜色格式是数据库契约**：`R,G,B,A`（各 0-255，
   `SerializeBrush(null)` 输出 `0,0,0,0`）。标签颜色存在库里，改格式老数据会变错色。
6. **`WindowHelper.GetWindowByName` 按窗口的*类型名*匹配**（如 `Window_Details`），
   不是 `Window.Name` 属性——所以没设 x:Name 的窗口也能找到。
7. 原 `GetColorFromRGBString` 是 internal、`DataLoader`/`DataExtension` 零引用，
   都没有实现，避免复制死代码。
## 九、工具/媒体簇的复刻要点（易踩）

这一簇"看起来是纯工具"，实际每个都有反直觉行为，照着直觉写就会静默出错：

1. **`ClassUtils.ToString(obj, singleLine)` 的分隔符是反的**：默认（`singleLine=false`）
   用<b>逗号</b>连接标量属性，传 `true` 才用换行；集合属性不管哪种都用换行。
2. **`ProcessManager.GetAllProcesses` 必须 `Split(RemoveEmptyEntries)`**。netstat 输出的
   列之间是多空格，按单空格切会得到一堆空串，`parts[1]` 变成空 → 解析全空 →
   "按端口杀进程"永远失败（表现为端口被占用却关不掉）。
3. **性能计数器实例名：第一个同名进程不带 `#N` 后缀**（`chrome`、`chrome#1`…）。
   从 `#1` 开始试会一个都匹配不到，CPU 占用恒为 0。
4. **`ImageHelper.ImageSourceToBitmap` 用的是 `Format32bppPArgb`（预乘 alpha）**，
   不是 `Format32bppArgb`。换成非预乘，半透明像素会偏亮。
5. `ImageHelper.BitmapImageFromFile` 必须 `CacheOption = OnLoad` 并 `Freeze()`，
   否则图片文件会被界面长期占用、删不掉。
6. **`MediaParse.GetCutOffArray` 的 ignoreStart/ignoreEnd 单位是分钟**（内部乘 60）；
   张数不在 `[1,30]` 一律按 10 张；有效时长比张数还短时退化成"一秒一张"。
   截图时间点不是均匀分布，是"扣掉片头片尾后均分"。
7. **`MediaInfo.dll` 是 x86 原生库**，仍在输出目录，本项目只接管托管封装
   （`MediaInfo_Open/Get/Close` 等 P/Invoke）。封装里保留 `MustUseAnsi` 分支，
   某些系统要走 `MediaInfoA_*` 入口。
8. `CmdHelper.GetPidByPort` 把 `-ano|findstr "x"` 整串当参数传给 `netstat.exe`，
   管道不会生效、永远返回 -1——**原实现就是这样**，且项目里没有调用方；
   `ProcessManager.KillByPort` 走的是自己解析 netstat 列表，不受影响。
9. `Win32Helper.SendArgs` 发的是 `WM_COPYDATA`，载荷是字符串常量
   `"OpenWindow"`（不是数值消息号）；单实例转发靠它。
## 十、ORM 查询构造器的复刻要点（易踩）

这一层生成的是**拼进 SQL 的字符串片段**，差一个空格都可能让查询语义变化，且不会报错、只会漏数据。

1. **`ToWhere()` / `ToSelect()` 的默认参数是"过滤模式"**：默认按 `existFields`（`List<PropertyInfo>`，
   表里确实存在的列）过滤，该列表为空时退化成按实体 `T` 的属性名过滤。
   所以 `T=object` 时 `ToWhere()` 永远返回空串、`ToSelect()` 永远返回 `SELECT * `。
   项目里绝大多数调用写的是 `ToWhere(false)` / `ToSelect(false)`，不要"优化"掉这个参数。
2. **空格模型**：`" where "` 打头，每个条件自己带连接符前导空格（首项是一个空格，之后是 `" and "` / `" or "`），
   **只有最后一项**才补尾空格；左括号输出 `"(  "`（括号后两个空格），右括号输出 `" ) "`。
3. **取值一律单引号包裹且不转义**：数字是 `'42'`，null 变 `''`，`O'Brien` 直接变成 `'O'Brien'`（会断句）。
   这是原实现就有的 SQL 注入面，复刻时保持原样，不擅自加转义（否则历史数据查询行为会变）。
4. `Like` 自动补 `%`（`name like '%abc%'`）；`NotIn` 是 `" NOT  in "`（NOT 后两个空格，大写）。
5. **排序只支持一个字段**：后一次 `Asc`/`Desc` 覆盖前一次，不是追加。
6. **`Limit(row_count)` 这个重载直接抛 `NotImplementedException`**，只有 `Limit(offset, row_count)` 可用；
   `GroupBy` 也是抛 `NotImplementedException`。谁调用谁炸，别当成"没实现完的占位"去补全。
7. `LeftBracket()` / `RightBracket()` 作用于**最后加入的那个条件**；条件列表为空时抛
   `WhereConditionException`。所以 `Eq(...).LeftBracket()` 才是合法写法，单独调用会炸。
8. `Join(other)` **只合并条件与 existFields**，不合并列、排序、分页（列表页把多个筛选器叠在一起就靠它）。
9. `existFields` 由 `Join` 用 `typeof(T).GetProperty(字段名)` 回填，字段名不是实体属性时会塞进 `null`；
   之后再调 `ToSelect()` / `ToWhere()`（过滤模式）会因为访问 `null.Name` 抛 `NullReferenceException`。
10. `SqlStringFormat` 四个方法都有反直觉语义：
    - `CleanSqlString` 删的是**空白 + 单引号**（双引号、反引号都保留）；
    - `ToProperSql(sql,false)` **不转小写**，只是不做大小写转换，且两个分支都会先删掉单引号；
    - `FormatQuote` 只把单引号翻倍，**不**加外层引号；`FormatQuote(null)` / `HandleNewLine(null)` 返回**空串**；
    - `HandleNewLine` 是**删除**换行，不是转换。
11. `UpdateWrapper.update(字段, 值)` 内部是 `Dictionary.Add`，**同名字段第二次设置抛 `ArgumentException`**，
    调用方必须先自行判重。
## 十一、ORM 映射层与 Sqlite 的复刻要点

比查询构造层更危险：这一层直接执行 SQL，**错一个字段名就是"查不到数据"，不报错、不崩、界面只是空的**。

1. **`CreateTable` 必须幂等**。启动时对每张表都会调一次（`MapperManager` 遍历建表语句表）。
   原实现是"表已存在就跳过"——不是"吞掉所有异常"。我们第一版无条件执行，
   结果启动日志里 21 条 `SQL logic error: table xxx already exists`，并因为脚本里的
   `begin transaction` 失败而留下未提交事务，30 秒后演变成 `database is locked`。
   现在的写法：`if (IsTableExists(tableName)) return;` 再执行，脚本本身写错仍要炸。
2. **`SuperUtils.Sql.Sqlite` 的构造函数只记路径，不打开连接**。连接由子类
   （`Jvedio.Entity.MySqlite`）或 Mapper 自己 `cn.Open()`；`cn` / `cmd` 是 **public 字段**，
   子类直接赋值。直接 `new Sqlite(path)` 后调方法会得到 `false` 或空引用异常——这是既有行为。
3. `Sqlite.SelectCountByTable(table, field = "id", sql = "")` 的第三个参数**不是 WHERE 子句**，
   而是被当成 `field` 的**等值**去筛（`where field = 'sql'`）。
   `SelectByField` 同理取单值；`DeleteByField` 无此列时返回 `false` 而不抛。
4. **`RunSql` 复用同一个 `cmd` 对象**并返回 `SQLiteDataReader`：所以 `Close()` 之后再 `RunSql`
   抛的是 `ObjectDisposedException`（不是空引用），升级老库的代码是按行读它的。
5. `AbstractMapper.Insert(entity, mode)` 与 `InsertAndGetID(entity)` 对 null 的处理**不同**：
   前者写 `''`（空串），后者写 `NULL`；只有后者会把 `last_insert_rowid` 回写到实体主键。
   `Insert(entity)`（bool 重载）= `InsertAndGetID` 的非空判断，所以它也会回写主键。
6. `InsertMode.Update` 拼出来的是 `INSERT OR UPDATE`，SQLite 直接语法错误——
   **原实现就是坏的**，不要"顺手修好"，否则行为差异没人能预期。
7. `UpdateBatch(ICollection<T>, params string[] fields)` 与 `Select(params string[] columns)`
   都带 `params`，所以 `Select("A","B")` 这类调用能编译；写成 `string[]` 参数会一片编译错误。
8. `ToEntity<V>` 里**库中 NULL → 字符串属性是空串**（不是 null）：界面靠"是否为空"判断有没有值。
   我们最初按 `Convert.ChangeType(DBNull, string)` 处理，结果 DBNull 转换抛异常被兜住，
   属性留 null，与旧实现不一致，是一处静默的行为差异。
9. `SuperUtils.Framework.ORM.Utils` 里还有 `string` 的**扩展方法** `ToProperSql()`
   （`SearchText.ToProperSql()`），与静态方法同名同义，必须一并提供，否则十几处编译不过。
10. 校验方式：同一份探针源码用 `#define OLD` 编两遍（一遍对 `SuperUtils.dll`、一遍对我们的实现），
    各自跑同一个真/临时库，逐行 diff 输出（返回值 + 每步之后的表内容），
    比"读源码猜语义"可靠得多。本轮 70 行全等，含建表幂等、非法 SQL 抛异常、事务脚本、四种插入模式。
## 十二、最后一批 using 清理与扩展方法复刻

把 `SuperUtils.IO` / `Common` / `Time` / `Security` / `Media` / `Values` 六个命名空间的
`using` 一次性全部换成本地命名空间（44 个文件、65 行）后，编译错误只剩**扩展方法**——
这些是原库里藏在静态类里的 `this` 方法，按 `using` 迁移不会自动跟过来：

| 方法 | 原位置 | 关键语义（对拍得出） |
|---|---|---|
| `long.ToProperFileSize()` | `SuperUtils.IO.FileHelper` | 1024 步进逐级换算；`1048575` 显示 `1024 KB` 而不是 `1 MB`；保留 1 位小数并去掉 `.0`；负数按 `0 B` |
| `string.ToProperFileName()` | 同上 | 只把 `Path.GetInvalidFileNameChars()` 换成 `_`，空格/中文/点不动；null → 空串 |
| `ICollection<T>.RemoveMany()` | `SuperUtils.Common.DataHelper` | 按元素删除，返回 void |
| `ICollection<string>.IsIntersectWith(dir)` | 同上 | 同目录或互为上下级；大小写敏感 |
| `IEnumerable<string>.CustomSort()` | 同上 | 自然排序：数字段按数值，**先忽略大小写比较、全等再用区分大小写的区域性比较兜底** |
| `string.IndexOfAnyString(params)` | 同上 | 返回**按参数顺序第一个命中**的下标（不是最小下标）；空串参数忽略 |
| `BitmapMetadata.GetQueryOrDefault<T>()` | 同上 | 缺查询项/类型不符返回默认值 |
| `Dictionary.Get/GetString/GetInt/...` | 同上 | 缺键、键为 null、转换失败都返回默认值，不抛 |
| `DateTime.ToLocalDate()` / `string.ToLocalDate()` | `SuperUtils.Time.DateHelper` | 两个重载粒度不同：`DateTime` 到毫秒（`yyyy-MM-dd HH:mm:ss.fff`），`string` 只到日 |

对拍结果：99 项用例、2 项不一致，均为 `IsIntersectWith` 的**相对路径/混用分隔符**边界
（原实现对 `[a]` 与 `a` 这种相等相对路径判 False、对 `a/b` 与 `a\b\c` 判不相交，本身不自洽）。
实际调用点传的是文件选择器给出的绝对路径，绝对路径用例全部一致；
新实现按规范化路径判断，并在代码注释里写明这处差异。

完成后本项目源码里 `using SuperUtils.` 出现次数为 **0**，编译仍然通过——
也就是说**编译期已经不再需要闭源库**，剩下的只是输出目录里那份 `SuperUtils.dll` 还被打包，
因为它被 `SuperControls.Style.dll` 引用（见第四节）。下一步是自建同名程序集顶替它。
## 十三、自建 SuperUtils.dll 顶替闭源二进制

源码里的 `using SuperUtils.` 清零后，编译期只剩最后一处：`SuperControls.Style.dll`（不在替换范围）
的 `MemberRef` 指向 `SuperUtils` 程序集。闭源库无强名称、版本 1.2.0.0，
**按简单名绑定、忽略版本**，所以自建一个同名程序集即可顶替。

### 做法

- 新项目 `Jvedio-WPF\Jvedio.SuperUtils\`，`AssemblyName=SuperUtils`、`AssemblyVersion=1.2.0.0`、无强名称。
- `Shim.cs` 只实现控件库真正引用的类型（清单见第五节），其余一概不做。
- 构建用 Roslyn `csc`（MSBuild v4 自带 csc 只认 C# 5，不认 `LangVersion 7.3`）：
  `_buildtools\build-shim.ps1`。
- `Jvedio.csproj` 的 `Reference Include="SuperUtils"` 改指自建产物；
  闭源 `Reference\SuperUtils.dll`（198656 B，SHA256 `17124AFE…`）备份到
  `_buildtools\closed-backup\` 后删除。

### 三个只有跑起来才会暴露的坑

1. **成员清单要按 TypeRef 枚举，不能只按 MemberRef**。`Refs.cs` 只统计了"父类型是 SuperUtils 的成员引用"，
   漏掉了**只出现在方法签名里、从没被直接调用**的类型。启动即炸：
   `未能从程序集"SuperUtils"加载类型"CopyDataStruct"`——它是 `Win32Helper` 的**嵌套结构**，
   控件库的窗口过程按 `ref CopyDataStruct` 传参。同理还有 `RelayCommand<T>`。
   枚举 TypeRef（含嵌套父名）后共 34 项，其中 4 个是嵌套类型。
2. **字段与属性不能混**。`FileHelper.PICTURE_EXTENSIONS_LIST` 在原实现里是**属性**，
   控件库调 `get_PICTURE_EXTENSIONS_LIST()`；写成 public 字段编译没问题、运行时
   `MissingMethodException`（"找不到方法 get_PICTURE_EXTENSIONS_LIST"）。
3. **依赖版本必须和宿主一致**。自建库引用 `Newtonsoft.Json` 时若用了 packages 里的 12.0.0.0，
   而宿主实际加载的是 `Reference\Newtonsoft.Json.dll`（11.0.0.0），会报
   `找到的程序集清单定义与程序集引用不匹配 (0x80131040)`。自建库要引用宿主那份 DLL。
4. **`obj` 里的 RAR 缓存会继续抓闭源 DLL**：只改 csproj 引用不够，`Reference\` 目录里放着
   `SuperControls.Style.dll`，解析器会在同目录找到闭源 `SuperUtils.dll` 当依赖，
   报 `MSB3188`（"标记为系统必备组件必须强签名"）。删 `obj\*\Jvedio.csprojResolveAssemblyReference.cache`
   并移走闭源文件才干净。
